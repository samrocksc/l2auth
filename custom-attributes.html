Custom Attributes → Token Claims

## The One Sentence Custom data lives in the **user profile**. A **claim** is only what you explicitly **project** from that profile into a token. Nothing ships in a token by accident — you have to whitelist it, map it, and put it in the right token. --- ## 1. Profile Data ≠ Token Claims This is the reframe that the old diagram missed. | | Profile Attribute | Token Claim | |--|-------------------|-------------| | **What it is** | Stored data about the user | A key-value pair projected into a token | | **Where it lives** | The identity profile (schema) | The signed token payload | | **How it gets there** | Manually, via sync, or from an IdP | Only by explicit mapping/projection | | **Is it visible?** | Only to whoever can read the profile | Visible to anyone who can decode the token | The mistake most people make is assuming "I added a custom attribute, so it'll just appear in the token." **It won't.** An attribute is inert until you project it into a claim. --- ## 2. Where Custom Data Lives (The Storage Model) ### Okta Custom attributes are added to the **user profile schema** — either in the **Profile Editor** (admin UI) or via the **Users API** (`/api/v1/meta/schemas/user/default`). You define the attribute, its type, and whether it's required/read-only. You can also populate attributes from **group membership** (group attribute mappings). ### Auth0 Auth0 splits custom data into **two namespaces**, and the distinction matters a lot: | | `app_metadata` | `user_metadata` | |--|----------------|-----------------| | **Who writes it** | Admin only (Dashboard / Management API) | The user themselves (when your app writes it) | | **What it's for** | **Authorization** data: roles, plan, permissions, flags | Non-critical **preferences**: theme, language, newsletter opt-in | | **Can the user self-edit it?** | No | Yes | | **Security posture** | Trusted — treat as authz source of truth | Untrusted — never base authorization decisions on it | > **Rule of thumb:** authorization data → `app_metadata`; preferences → `user_metadata`. If a user could self-escalate by editing a value, it belongs in `app_metadata`. --- ## 3. The Projection — Turning an Attribute Into a Claim This is the step the profile → token diagram compressed into one box. It's actually two. ### Okta Map profile attributes to claims inside an **Authorization Server** (the **Default** AS or a custom one). You configure which attribute becomes which claim, and you scope it to the **ID token**, the **access token**, or both. ``` Custom Profile Attribute → Claim Mapping (AS config) → Token Claim ``` ### Auth0 Two pieces: 1. **Whitelist the metadata** so it *can* appear in the token. 2. Write a **post-login Action** (JavaScript) to add or copy the claim into the token. ```js exports.onExecutePostLogin = async (event, api) => { // Copy a value from app_metadata into the access token api.accessToken.setCustomClaim("roles", event.user.app_metadata.roles); // Or from user_metadata into the ID token api.idToken.setCustomClaim("theme", event.user.user_metadata.theme); }; ``` Without a whitelist and an Action (or a Rules rule), your custom attribute will **not** appear in any token. --- ## 4. Which Token, For Whom? The old diagram showed a generic "JWT" — but *which* token you target changes the semantics. See [ID Token vs. Access Token](./concepts/id-token-vs-access-token.html). | | ID Token | Access Token | |--|----------|--------------| | **Audience** | Your app (frontend) | Your API (backend) | | **Purpose** | Identity — *who* the user is | Authorization — *what* the user can do | | **Custom authz claims (roles, permissions) belong?** | ❌ No | ✅ Yes | If you're adding **roles or permissions** to make authorization decisions at your API, put them in the **access token**, not the ID token. The ID token is for identity; it shouldn't be sent to your API. --- ## 5. The RBAC Gotcha Adding **permissions** to an Auth0 access token is a two-part switch: 1. Enable **RBAC** on the API. 2. Toggle **"Add Permissions in the Access Token"** on that API. **Enabling RBAC alone is not enough.** The permissions only land in the access token when that second toggle is on. This is the classic "I enabled RBAC but my token has no permissions" trap. --- ## 6. Scopes Gate the Claims Requested **scopes** determine which claims come back — scopes are the *request*, claims are the *response*. (See [Scopes vs. Claims](./concepts/scopes-vs-claims.html).) Standard claims (`openid profile email`) map automatically. **Custom claims usually need a custom scope** that your Authorization Server recognizes and that your client requests. If the client never asks for the scope, the custom claim stays out of the token even though you mapped it. ``` Request: scope=openid profile roles → Response: sub, name, ..., roles Request: scope=openid profile → Response: sub, name, ... (no roles!) ``` --- ## 7. Security & Hygiene - **Don't put sensitive data in tokens.** Tokens travel through the browser and can be large. Keep PII out; prefer a `userinfo` call or a backend lookup for heavy data. - **Keep `app_metadata` admin-controlled.** If users could write authz data, they could escalate their own privileges. Only trust `app_metadata` for authorization decisions. - **Keep tokens lean.** Every claim adds weight to every request. Project only what you actually consume. - **Map once, don't duplicate.** Prefer a single source of truth in the profile over duplicating values into several claims. --- ## The Full Lineage ``` STORAGE PROJECTION TOKEN ┌─────────────────────┐ ┌──────────────────────┐ ┌──────────────────┐ Okta │ User Profile Schema │ ───▶ │ AS Claim Mapping │ ──▶ │ ID / Access Token│ │ (custom attribute) │ │ (scoped per token) │ │ │ └─────────────────────┘ └──────────────────────┘ └──────────────────┘ Auth0 │ app_metadata (authz)│ │ Whitelist + Post-login│ ──▶ │ Access Token │ │ user_metadata (pref)│ │ Action (JS) │ │ ID Token │ └─────────────────────┘ └──────────────────────┘ └──────────────────┘ ``` **Key takeaway:** storage → projection → target. Pick the right store, project explicitly, and target the correct token. Get any of the three wrong and your custom data either never reaches the token — or worse, reaches the wrong one.
